# Приём заявок и безопасный запуск

## Что изменилось

Обе формы отправляют multipart POST, получают номер только после фиксации заявки в SQLite и сохраняют введённые данные при ошибке. Интерфейс подтверждает **сохранение**, а не доставку email. Уведомления получает подтверждённый владельцем адрес `Fedor.fiberflex@gmail.com` для RU и EN. Отправитель и SMTP настраиваются отдельно на сервере.

Node API — отдельный постоянно работающий процесс. **GitHub Pages исполняет только статический сайт**, не API. Нельзя считать исправление введённым на публичном сайте, пока обработчик не размещён, не настроены SMTP/антивирус и сайт не пересобран с его HTTPS адресом. Временный неработающий API не вызывает ложный успех: форма сообщает об ошибке и сохраняет поля.

## Локальная проверка

Требуется Node.js24.19+ (ветка24), npm11; используйте существующий checkout, без нового worktree. Команды из корня:

```sh
npm ci
npm test
ASTRO_TELEMETRY_DISABLED=1 npm run build
npm audit --audit-level=low
node tests/browser-smoke.mjs
```

Последняя команда требует установленного Playwright и Chromium; в облачном образе они доступны. Автотесты используют временную базу, имитацию SMTP и антивируса; реальные письма не отправляются. Тесты ClamAV проверяют протокол на локальном имитаторе, не заменяя обновлённый антивирус при размещении. `npm run dev -- --host 127.0.0.1` запускает только сайт; `/api` проксируется в локальный обработчик на127.0.0.1:8787. Без запущенного API отправка честно покажет ошибку.

Astro генерирует `.astro/types.d.ts`, который исторически отслеживается Git. Не коммитьте ненамеренные изменения этого файла; сохраняйте и восстанавливайте текущую копию, включая пользовательские изменения, перед проверками генератора. Зависимости и база сохраняются на диске; процессы необходимо запускать заново.

## Обязательные настройки production

1. Выбрать сервер с постоянным диском и Node24. Не использовать ephemeral filesystem/serverless SQLite. Запускать **один процесс** API/worker с одной базой на локальном диске; горизонтальное масштабирование потребует другой очереди/БД. Не открывать порт8787 в Интернет, только HTTPS reverse proxy.
2. Согласовать место хранения персональных данных, поставщиков обработки и сроки. Оператор из действующего сайта — ООО «Акцепт-2». Проверьте юридическое основание, локализацию, необходимость уведомлений/договоров перед сбором данных. Checkbox не заменяет эту проверку. Нельзя утверждать юридическое соответствие по одному коду.
3. Выбрать SMTP-провайдера и подтверждённый адрес отправителя, проверить SPF/DKIM/DMARC этого домена. Получатель Gmail не означает, что отправителем обязан быть Gmail. SMTP-ключи/пароли вводить **только в защищённые настройки сервера**. Никогда не в Git, браузерный JS или GitHub `PUBLIC_*` variables.
4. На сервере создать системного пользователя `acceptmetall`, разместить checkout в `/opt/acceptmetall-site`, выполнить `npm ci --omit=dev`. Создать закрытый `/etc/acceptmetall/orders.env` по `server/.env.example`; права0600, владелец пользователь сервиса. `ORDER_ADMIN_TOKEN`: случайный токен минимум32 символа, например `openssl rand -hex 32`; не использовать публичные/предсказуемые значения. `ORDER_DB_PATH=/var/lib/acceptmetall/orders.sqlite` должен быть на постоянном диске. Владелец каталога — пользователь сервиса, права0700.
5. `ORDER_ALLOWED_ORIGINS` — точные HTTPS origins сайта через запятую, например `https://acceptmetall.ru`. Не добавлять `*`, URL путей или посторонние сайты. `ORDER_TO` по умолчанию подтверждённый Gmail; можно задать явно. `ORDER_FROM`, `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD` обязательны; `SMTP_PORT=465` (TLS) или587 (обязательный STARTTLS). Проверка сертификатов включена. `ORDER_ADMIN_TOKEN` не передавать в клиент.
6. Установить/обновлять ClamAV и сигнатуры freshclam. В приватной конфигурации clamd включить TCP127.0.0.1:3310 и StreamMaxLength не меньше5MiB. Никогда не открывать3310 в Интернет. API использует INSTREAM, ему не нужен доступ антивируса к файлам. `CLAMD_HOST/CLAMD_PORT` указывают этот приватный экземпляр. Если сканер недоступен, заявка **с файлом отклоняется**, а форма сохраняет данные; без файла приём доступен. Проверить реальную работу сканера перед включением вложений.
7. Шаблоны `deploy/acceptmetall-orders.service` и `deploy/Caddyfile` требуют адаптации к фактическим путям Node и домену; они не установлены автоматически. systemd создаёт закрытый StateDirectory. Установить service, daemon-reload, enable/start после заполнения настроек. Caddy должен иметь DNS/доступ80,443 для сертификата. Не отключать TLS verification при ошибках. `ORDER_TRUSTED_PROXIES` задавать только точными приватными IP своего reverse proxy; иначе очистить. API игнорирует присланный клиентом X-Forwarded-For от остальных адресов.
8. На GitHub Pages создать Repository variable `PUBLIC_ORDER_API_URL=https://<домен-API>/api/orders`, пересобрать сайт. Адрес публичный и не содержит секретов. CI проверяет его перед публикацией; без адреса публикация блокируется, тесты/сборка доступны. CSP автоматически разрешает только origin этого обработчика. Если переносите сайт и API на один сервер, можно оставить `/api/orders` и настроить reverse proxy этого пути; приложенный Caddyfile обслуживает только API, не static dist.
9. Согласовать реальный тест с владельцем почты: отправить одну заявку, проверить её номер через защищённый API, вложение, затем получение письма и отсутствие спама. Ответ SMTP означает принятие почтовым сервером, а не гарантированное попадание в Inbox. Автоматическое подтверждение клиенту по email не включено, чтобы не создавать открытый почтовый ретранслятор.

## Заявки, очередь и контроль доставки

Защищённый API требует `Authorization: Bearer <ORDER_ADMIN_TOKEN>`:

- `GET /api/admin/orders?offset=0` — последние100 записей, `nextOffset` для следующей страницы и общее `pendingNotifications`.
- `GET /api/admin/orders/<UUID>` — поля, время, статус уведомления и число попыток.
- `GET /api/admin/orders/<UUID>/attachment` — принудительное скачивание проверенного файла. Файлы и база не лежат в `public`/`dist`. У файлов серверные имена.

Для обращения используйте защищённый API-клиент, который хранит токен вне истории shell/URL. Без токена заявка и файл недоступны. Не размещать токен в статической «админке». Это API управления, а не готовая браузерная CRM.

Worker проверяет очередь каждые5 секунд, повторяет ошибки с задержкой от30 секунд до1 часа. Потеря SMTP не удаляет заказ. `notificationStatus=sent` означает SMTP accepted, не подтверждение прочтения/Inbox. Доставка имеет семантику **at least once**: при аварии после приёма SMTP до записи результата возможен повтор письма; стабильные номер и Message-ID помогают распознать его. Идемпотентность HTTP создаёт ровно одну запись на одинаковый ключ и тело, но не обещает exactly-once email.

Нужен внешний мониторинг: проверять `/healthz` (только живой API), приватный `pendingNotifications`, старые pending-заявки/число попыток и системные события `order_notification_retry` / `outbox_worker_failed`. События не содержат полей заказа/почтовых ответов. Настроить оповещение дежурному выбранным владельцем способом. Сам по себе health200 не подтверждает SMTP, свежесть сигнатур или отсутствие очереди. Публичные заголовки, доступность SMTP, DNS и внешние оповещения требуют проверки на размещённом сервере.

## Защита и срок хранения

- Серверная allowlist полей, пределы длины, размера файла5MiB/запроса, тип по содержимому+расширению, обязательные согласие и контакты, honeypot и лимит запросов с Retry-After. Origin проверяется дополнительно; публичную форму нельзя полностью защитить от спама одним CORS. При целевом потоке ботов добавьте managed challenge на reverse proxy без изменения сохранения заявок.
- Прилагаются только PDF/JPEG/PNG, исходные имена заменяются; Office-архивы больше не обещаются формой. Вложения проверяются антивирусом до записи/отправки. Доступ закрыт bearer-токеном; отдельные роли пользователей/веб-CRM не реализованы.
- SQLite WAL, synchronous FULL, права файла0600/каталога0700, secure_delete. Приложение удаляет заказы и вложения старше `ORDER_RETENTION_DAYS` (по умолчанию90) при старте/работе очереди/обращении. Срок в опубликованной политике должен соответствовать настройке; при изменении пересоберите политику. Физическое удаление остатков из WAL, резервных копий, почтовых ящиков и внешних систем требует отдельной политики эксплуатации. Подготовьте шифрованные резервные копии SQLite штатным backup-механизмом, проверьте восстановление; не копируйте только основной файл во время WAL-записи. Не сохраняйте резервные копии навечно.
- Секреты и SQLite игнорируются Git. Для диска/резервных копий включите шифрование на хостинге; приложение само не обещает шифрование базы.
- Astro генерирует CSP с хешами встроенных скриптов/стилей; убраны внешние шрифты. HSTS, X-Frame-Options и другие HTTP-заголовки для API заданы в шаблоне proxy и API. GitHub Pages не поддерживает произвольные security headers: CSP meta не может выставить frame-ancestors/HSTS; для управления заголовками самого сайта нужен CDN/reverse proxy или другой хостинг. Не считать эти заголовки установленными на текущем сайте без внешней проверки.

## Что остаётся внешним действием

Код/тесты не размещают сервис, не создают почтовые ключи, DNS, сервер и мониторинг, не восстанавливают старую несохранённую заявку. Для завершения production нужны выбранный хостинг/место хранения, SMTP и проверка реальной доставки. Изменения не опубликованы автоматически.
